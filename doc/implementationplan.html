Tickit Implementation Plan

Bu plan, doc/rapor.html teknik raporunda tespit edilen eksikler, güvenlik riskleri, performans önerileri ve ürün geliştirme fırsatlarına göre hazırlanmıştır. Amaç, Tickit projesini daha güvenli, test edilebilir, ölçeklenebilir ve ürün olarak daha kullanışlı hale getirmek için uygulanabilir bir yol haritası sunmaktır.

Kaynak: doc/rapor.html Kapsam: Frontend + Backend + DB + Security Öncelik: Güvenlik ve veri bütünlüğü önce Yaklaşım: Fazlı uygulama

1. Plan Özeti

Rapor, projenin çalışır durumda olduğunu ancak production kalitesi için bazı kritik alanların tamamlanması gerektiğini gösteriyor. En önemli başlıklar request validation, NoSQL sanitization, test altyapısı, environment örneklerinin doldurulması, database indexleri, görev listesi ölçeklenmesi ve auth/token güvenliğidir.

4. Faz 1 - Backend Güvenlik ve Veri Bütünlüğü

Hedef

API'ye gelen verinin açıkça doğrulanması, sanitize edilmesi ve sadece izin verilen alanların create/update işlemlerine girmesi.

Önerilen teknik yaklaşım

  • Validation için zod veya express-validator seçilmeli. Kod okunabilirliği için zod önerilir.
  • Auth ve task schema'ları backend/src/validators/ altında toplanmalı.
  • Validation middleware backend/src/middleware/validate.js olarak eklenmeli.
  • Task controller içinde payload allowlist helper kullanılmalı.
  • NoSQL sanitize için express-mongo-sanitize veya eşdeğer middleware app.js içine eklenmeli.

Dosya bazlı uygulama planı

DosyaDeğişiklik
backend/package.jsonzod, express-mongo-sanitize ve test bağımlılıkları eklenecek.
backend/src/app.jsJSON parser sonrası sanitize middleware eklenecek. Auth endpointleri için ayrı rate limiter bağlanacak.
backend/src/validators/authValidators.jsRegister/login body schema'ları oluşturulacak.
backend/src/validators/taskValidators.jsTask create/update schema'ları oluşturulacak.
backend/src/middleware/validate.jsSchema parse edip hata durumunda 400 JSON dönen middleware eklenecek.
backend/src/routes/auth.jsRegister/login route'larına validation middleware eklenecek.
backend/src/routes/tasks.jsPOST/PUT route'larına validation middleware eklenecek.
backend/src/controllers/taskController.jsCreate/update için allowlist payload uygulanacak.
backend/src/models/Task.jsColor formatı ve dueAt validasyonları gerekirse schema seviyesinde güçlendirilecek.

Validation kapsamı

EndpointAlanKural

Kabul kriterleri

  • Geçersiz request body için 400 ve anlaşılır hata mesajı döner.
  • Beklenmeyen alanlar DB'ye yazılmaz.
  • $ne, $gt gibi NoSQL operatörü içeren body'ler etkisiz hale gelir.
  • Mevcut frontend akışları validasyon sonrası çalışmaya devam eder.
  • npm run lint ve backend testleri geçer.

6. Faz 3 - Veritabanı ve API Ölçeklenmesi

Hedef

Görev sayısı arttığında API'nin stabil kalması, listeleme performansının korunması ve frontend'in gereksiz büyük payload almaması.

DB index planı

// backend/src/models/Task.js
TaskSchema.index({ user: 1, createdAt: -1 });
TaskSchema.index({ user: 1, completed: 1, createdAt: -1 });
TaskSchema.index({ user: 1, dueAt: 1 });

Pagination API tasarımı

ParametreÖrnekAçıklama
page1Sayfa numarası. Varsayılan 1.
limit20Sayfa başına görev. Maksimum 100.
statusactiveall, active, completed.
qraporBaşlık/açıklama araması.
sortdueAtcreatedAt, dueAt, priority.

Önerilen response yapısı

{
  "success": true,
  "count": 20,
  "total": 145,
  "page": 1,
  "pages": 8,
  "tasks": []
}

Frontend etkisi

  • dashboard/page.jsx içinde filtreler server query parametresine taşınır.
  • Client-side filtered hesaplaması ilk aşamada korunabilir, sonra server-side filtreye geçilir.
  • Liste altına "Daha fazla yükle" veya pagination kontrolü eklenir.
  • Search input ve sort select dashboard araç çubuğuna eklenir.

Kabul kriterleri

  • GET /api/tasks?page=1&limit=20 paginated response döner.
  • Eski frontend kırılmaması için default response alanları uyumlu kalır veya frontend aynı PR içinde güncellenir.
  • MongoDB query'leri user filtresiyle ve index dostu çalışır.

8. Faz 5 - Production Hardening

Hedef

Production ortamında gözlemlenebilirlik, güvenli secret yönetimi, net deployment davranışı ve daha güçlü auth stratejisi sağlamak.

Yapılacaklar

AlanÖneriKabul kriteri
Loggingpino veya winston ile structured logging.Request id, status, duration ve error stack kontrollü loglanır.
Error responseProduction'da stack yok; hata kodları standardize.API hataları tutarlı { success, message, code } formatında döner.
Auth storageHttpOnly Secure SameSite cookie + CSRF token PoC.XSS token çalma riski azaltılır; CSRF stratejisi açıkça uygulanır.
SecretsDeployment provider secret manager/env panel kullanımı.Repo içinde gerçek secret bulunmaz.
MongoDBMinimum yetkili DB user, IP allowlist, ayrı prod/dev DB.Prod ve dev verileri ayrılır.
Rate limitAuth endpointleri için düşük limit, genel API için ayrı limit.Brute-force ve abuse riskleri azalır.
